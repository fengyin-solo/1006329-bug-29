# 城市地下综合管廊运行维护管理平台

面向管廊主体台账、入廊管线登记、廊内环境监测、通风排水消防、结构沉降与渗漏处置、巡检检修与隐患整改、入廊作业审批和运维值班的一体化城市地下综合管廊运行维护管理工作台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `urban-utility-tunnel:entries` 这一项，或调用 `resetModule(模块)`。

## 业务规则与仲裁依据

### 流转次序固定，跳档一律打回

- 每个动作在 `modules.ts` 的 `actionSources` 里登记了允许的发起状态，从待办到归档的次序
  以此为准；页面只渲染当前状态下合法的动作，服务端（`runAction`）再校验一次。
- 跳档请求一律打回，并在提示里写清卡在哪一段、应从哪一段推进，例如：
  「MAIN-0001」当前卡在「待开工」段：「确认完工」需从「检修中」或「已延期」推进，跳档一律打回。
- 检修链路：待开工 → 检修中 → 已完工；检修中可申请延期（可再次延期），已延期仍须完工归档。

### 检修完工一次落库，重复完工只落一次

- 确认完工是一个事务：检修记录的 状态 / 完工日期 / 更换部件 / 完工结论 与设备台账新增的
  一条「待保养」保养计划在 `saveAll` 里整库一次写入，不写半截。更换部件必填（未更换填「无」）。
- 完工结论写入设备台账新行的「保养计划」列，并记录来源检修编号。
- 幂等：已完工的记录再点完工会被顺序校验打回；设备台账按来源检修编号去重，同一记录
  重复完工不会落第二次、不会多出一行。
- 列表与详情读同一份本地库（`getEntry` 与 `listEntries` 同源），两处必然一致。

### 存量检修记录计划工期回填（裁决规则）

读库时自动跑幂等迁移（`frontend/src/data/migrate.ts`）：

1. 「计划工期」缺失或写法不标准的，按检修类别套标准工期回填：大修 15 天、中修 7 天、
   小修/保养/巡检 3 天；类别辨认不出的取默认 7 天。
2. 早年只有完工日期、没有计划工期的，再按「完工日期 − 标准工期」倒推计划开工日，
   并把回填依据写进「工期回填」留痕字段。

依据：回填值只作计划基准、不改完工事实；默认 7 天与中修一致，是各类检修里最接近
中位数的档位，倒推偏差最小。迁移同时把各模块末尾的「XX状态」字段与记录状态镜像一致，
消除列表与详情两处对不上。

### 判定冲突：以新判定为准，旧判定只留痕

- 判定类动作（判定正常/标记超标、确认核对/标记异常等）允许从对方终态改判；
  改判时新判定为准，旧判定写入「流转留痕」，只作审计痕迹不再作准。
- 依据：改判发生在复测/整改之后，后一次判定基于更新的数据，理应作准；
  旧版留痕保证可追溯。

### 往期单据导入：同一份材料只留最早一版

- 能耗模块「导入往期单据」：电子单据按「计量点位+统计周期」建账，早期纸面单据按
  「扫描件编号」建账；往期单据一律以「已核对」归档，导入明细与台账现状同源一致。
- 仲裁规则：同一份材料重复导入，以最早入帐那一版为准——内容一致的直接忽略；
  内容有出入的按冲突处理，仍以最早版为准，导入版只在该行「导入留痕」里留痕，
  台账不多出一行。
- 依据：最早入帐的一版最接近抄表/扫描的原始凭证时点，后续重复导入视为重复报送
  而非更正；要更正应走「标记异常 → 确认核对」的改判链路，不走重复导入。

### 上报问题 → 遗留清单，两处条数一致

- 巡检「上报问题」在同一事务里把遗留事项落到值班交接的遗留清单（按来源巡检编号去重）。
- 巡检页的已上报数与值班页的遗留清单条数都由 `backlogSummary()` 从同一份数据算出，
  两处始终一致。
